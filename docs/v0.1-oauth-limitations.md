# v0.1 OAuth behavior and limitations

v0.1 requires refresh-family enforcement and `0008_refresh_token_family.sql`.
Apply the migration before compatible Worker code as part of an authorized
rollout. This describes source behavior; it is not evidence of a deployment or
of acceptance with real clients.

- Each enrolled Dot or Claude grant has one family in D1, storing only one-way
  refresh-token hashes. Claims serialize issuance before grant or token writes.
  A concurrent lock loser receives temporary 503 with `Retry-After: 1`, leaving
  time to retry inside the recovery window.
- The immediately previous refresh token can be used once within about
  60 seconds. A second use, later use, or reuse of an older recorded or displaced
  token revokes the family and credential.
- The current refresh token rotates at most once every 15 minutes. An earlier
  rotation receives temporary 503 with `Retry-After` set to the remaining
  seconds and writes nothing. A current-token admission whose grant read fails
  after the claim starts that same interval, so later current-token attempts
  in the interval write no D1 row. That charge does not reopen an expired
  previous-token grace or extend one that is still open. A failed grace-token
  retry is not charged. A revocation whose first grant read succeeds and whose
  confirming read throws, or returns a different grant, is not charged either:
  the claim is released and the next request can claim again. Capping that
  revocation path needs a new column, and v0.1 adds no schema. It is an
  accepted limitation. A first read that throws writes nothing. While a claim
  is held, another eligible revocation writes no row. The one-use grace retry
  is exempt, so one chain rotates at most twice per interval.
- A family records at most 5,764 hashes, the most its 30-day grant can reach
  under that budget. History is not pruned while the grant can refresh, so reuse
  of any recorded ancestor still revokes the family. A family at the bound is
  refused and revoked rather than extended.
- Owner and family reuse revocation set `revoked_at` in place. Refresh and
  existing access tokens are refused on the next request, without waiting for
  access-token expiry. Replaying an exchanged authorization code preserves
  whole-grant revocation, synchronized with the matching D1 family.
- Setting `participant.enabled` to 0 returns 503 with `Retry-After: 60` on
  `/token` and `/mcp` for otherwise valid OAuth credentials. The grant, family,
  and credential are preserved; the same client continues after re-enable.
  A rotation already admitted before the pause may finish safely.

Residual limits:

- Existing grants enroll at their first provider-validated refresh. Tokens
  from before enrollment are not fully recorded, so an unknown historical
  token can be refused without enough history to revoke a family. No
  retrospective ancestor-detection guarantee is made.
- A crash during refresh can leave a family claimed. Refreshes then return
  503 until owner revocation and reconnect. There is no automatic takeover,
  and re-enabling does not clear an abandoned claim.
- Rolling back to Worker code without family enforcement removes reuse
  detection and the refresh budget while that code runs. Refreshes during that
  window can desynchronize provider and D1 state. After rolling forward, an
  unrecorded provider-valid token gets `400 invalid_grant` when no claim is
  pending; revoke affected credentials and reconnect rather than clearing
  family history.
- A client that refreshes during the 15-minute interval is deferred. A
  transient KV failure on a current-token grant read starts that same interval.
  Once the access token has expired, the client cannot refresh until the
  interval ends: 503 with reason `refresh_budget` and `Retry-After` up to 900,
  which is 15 minutes.
- Protocol revocation of an individual access token affects only that token.
  The original 30-day grant lifetime is unchanged.

The unwrapped provider has no timed previous-token grace; its reuse policy is
bounded by grant expiry or advancement using a replacement. Existing D1
credential guards can enforce revocation independently of that provider-only
behavior. Verify the installed build separately before an authorized rollout.
